# AWS-1: Bedrock diagnostic provider

AWS-2 now adds a separate trusted local ResultsCX preparation path. See [AWS-2 real evidence boundary](aws2-real-evidence-boundary.md) for current real-data behavior; the synthetic-only statements below describe the original AWS-1 gate.

AWS-1 implements only the M3 diagnostic reasoner. M2 produces deterministic QA signals and coverage. M3 builds and validates the evidence bundle, then the Bedrock adapter projects an allowlisted synthetic payload, calls Bedrock Runtime `Converse`, validates the JSON response, resolves opaque citations locally, and returns a normal M3 hypothesis. The existing M3 human Approve / Reject / Revise workflow follows. The adapter uses `boto3` because it is the AWS SDK that supplies Bedrock Runtime `Converse` and the normal AWS credential provider chain; no credentials are stored here.

`COACHLENS_BEDROCK_ENABLED` defaults to `false`. When true, the normal API and explicit ResultsCX demo install a `BedrockReasoner` and `/diagnostics/mode` reports `diagnostic_provider: provider` together with `remote_diagnosis: privacy_blocked`, both read from the installed object. `diagnostic_provider: provider` alone never means real remote diagnosis is permitted; `remote_diagnosis` is `unavailable`, `local_fixture`, `privacy_blocked`, `synthetic_only`, or `undeclared`, and a provider cannot declare any other value. The invocation region defaults to `us-east-1`, and the system-defined inference profile defaults to `global.anthropic.claude-sonnet-4-6`. Override with `COACHLENS_BEDROCK_REGION` and `COACHLENS_BEDROCK_MODEL_ID`. Obtain temporary AWS credentials through the normal SDK environment, profile, or role chain outside Git. Never put credential values in `.env`, source, logs, or documentation.

## Privacy boundary

The selected **global** inference profile may route outside `us-east-1`. The existing local M3 provider view uses known-name redaction only; it is not anonymized and may contain PHI or PII in evaluator feedback. AWS-1 therefore refuses remote invocation by default, including when Bedrock is enabled with real ResultsCX records. The public `BedrockReasoner` constructor has no unlock; the only way to permit invocation is `BedrockReasoner.for_synthetic_evaluations(...)`, which binds the reasoner to the exact in-memory synthetic `Evaluation` objects passed to it. At diagnosis time the reasoner refuses any bundle whose evaluation identifiers or loaded population differ from that set, so the same object attached to a service holding other records still sends nothing. No setting, environment variable, request body, header, or query parameter creates or unlocks the binding; the smoke script is the only caller. The Bedrock payload includes a synthetic criterion label, domain, deterministic fail and evaluated result counts, failure rate, evaluations containing the criterion, total loaded evaluations, feedback count, and structured per-row pass/score facts. It excludes raw feedback, free-text answers, names, local evaluation and evidence IDs, filenames, paths, sheets, and `SourceLineage`. Opaque `SIGNAL-001` and `EVID-###` references are mapped back to local M3 IDs after validation. No free-text sanitization or HIPAA/PHI detection is claimed. The local reviewer evidence route retains its existing confidential evidence behavior.

Real ResultsCX remote diagnosis requires a separately reviewed provider-safety policy and tests. Enabling the setting alone does not permit it. Do not use the synthetic switch with workbooks or normalized real records.

## Synthetic smoke

From the repository root, install the API dependencies, supply temporary AWS credentials through the normal SDK chain, and run:

```sh
COACHLENS_BEDROCK_ENABLED=true python scripts/run_bedrock_synthetic_smoke.py
```

The script rejects a configured `COACHLENS_API_DIAGNOSTIC_EVALUATIONS_PATH`, builds four synthetic evaluations in memory, and binds the reasoner to exactly those records. It invokes Bedrock once, validates a normal `DiagnosticRecord`, and prints only a status, cause category, confidence, reference count, provider identifiers, and aggregate coverage. It does not print model reasoning, raw evidence, credentials, or request headers. The caller needs permission to invoke the selected inference profile. The normal API does not enable the synthetic switch.

## Output contract

The system prompt has two parts. `REASONING_PROMPT` carries the diagnostic rules and coverage semantics. `response_contract()` renders the exact output contract from the `BedrockResponse` JSON schema itself: every field with its JSON type, enum values, and length or range bounds, followed by per-field guidance for rules a schema cannot express (opaque reference citation, `missing_evidence` always a JSON array even with one item and `[]` when nothing is missing, `provider_reported_confidence` always a JSON number and never a label such as `low_to_moderate` or a percentage string), an explicit key allowlist that excludes `hypothesis_id`, `signal_id`, `provider_metadata`, `generation_mode`, and lineage, and a shape illustration that tests validate against the same model. Because types and bounds are read from the validator, a schema change appears in the prompt without a second definition to maintain. The prompt describes what local validation accepts; it does not replace it. The first live synthetic smoke returned `missing_evidence` as a bare string and a qualitative confidence label; both were refused and nothing was stored, which is the intended fail-closed behavior, and this contract exists so a conforming model does not produce them again. Confidence must arrive as a JSON number: a bool, null, or numeric string is refused before Pydantic's lax coercion could accept it.

Bedrock Runtime `Converse` also offers native structured outputs (`outputConfig.textFormat` with `type: json_schema`), which the installed `botocore` exposes and which AWS documents as supported for Claude Sonnet 4.6, including the global inference profile. AWS-1 does not use it. The `BedrockResponse` schema relies on `minLength`, `maxLength`, `minimum`, `maximum`, and `maxItems`, all of which Bedrock's supported JSON Schema subset rejects with a 400, so a second hand-projected schema would be required; first use of a schema compiles a grammar that AWS says can take minutes, against this adapter's 90 second read timeout; it would add a request field to the enumerated Converse request; and it could not be verified without a live invocation. Adopting it is a separate change that needs its own live smoke. Local validation would remain authoritative either way.

Malformed, semantically invalid, or uncited model output fails with a sanitized 502 response and stores no diagnosis; a turn whose `stopReason` is not `end_turn` (truncated, filtered, or guardrail-stopped) is refused even when its text parses. AWS errors also become a sanitized 502; the client uses explicit connect/read timeouts with standard-mode retries, and there is no fixture fallback. Only a fixed set of reasoner error codes with fixed messages can reach a client; any other reasoner exception is reported as `reasoner_failure`. A privacy-blocked real-data invocation returns 502 before an AWS client is created. The provider metadata records Amazon Bedrock, inference profile, invocation region, a request ID when available, and UTC generation time. `generation_mode` is stamped by `DiagnosticService` from the installed reasoner object (`provider` for Bedrock, `controlled_fixture` for the test fixture); output that asserts its own generation mode is rejected, in M3 and in M5 design validation. The diagnosis remains `awaiting_review` until a human acts.

AWS-1 does not implement intervention or training providers, evidence or solution validators, alignment guard, outcome evaluation, AgentCore, S3, DynamoDB, Lambda/API Gateway, voice, deployment, authentication, or changes to scoring, normalization, and human validation.
