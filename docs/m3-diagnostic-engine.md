# M3 diagnostic engine

## Three separate layers

**Fact:** M2 canonical `Evaluation` and `CriterionResult` records establish pass/fail, scores, feedback presence, and source lineage. M3 `PerformanceSignal` reuses M2 `analyze()` for deterministic per-criterion aggregates. It includes zero-failure criteria and ranks by descending fail count, then fail rate, then domain and criterion. This order is a transparent sort, not a ResultsCX severity policy. Rates are over the criterion rows present; `evaluated_evaluations` and `total_evaluations` state how many loaded evaluations the criterion actually covers, and `build_bundle` refuses a signal whose counts or `total_evaluations` disagree with the records it is served with. A signal has no causal category.

**Hypothesis:** `EvidenceBundle` links one signal to only its criterion rows. The aggregate signal and row-level `EvidenceItem` objects are distinct. Each item retains original evaluator feedback and source filename, sheet, and row internally. Item IDs are derived from the signal, evaluation ID, and source location, so they are stable across runs, unique across bundles, and cannot silently re-point at a different row when the underlying data changes. A provider-facing view drops lineage locations and applies the redaction described below. It retains pseudonymous evaluation IDs, item IDs, original criterion wording, pass/fail, scores, and feedback text. Internal M2 IDs are pseudonyms, not an anonymization guarantee.

### Privacy boundary (read before connecting any remote provider)

What the provider view removes: structured identity fields (agent, evaluator, and leader names) as fields; source filename, sheet, and row; and whole-word, case-insensitive occurrences of the exact recorded agent, evaluator, and leader name strings inside evaluator feedback.

What it does **not** remove: partial names, initials, and nicknames; member, patient, or caller names; email addresses, phone numbers, account, member, or medical record numbers; street addresses; dates of birth; or any other personal or health information that appears only inside free-text comments. Feedback text is otherwise sent verbatim. The view is identity-minimized, not anonymized or de-identified, and it makes no HIPAA or PHI claim. Before any Bedrock or other remote adapter receives real ResultsCX comments, CoachLens needs an explicit, separately reviewed data-minimization boundary (for example, excluding feedback text by default, or a reviewed redaction step). M3 deliberately does not ship a heuristic PII detector.

`DiagnosticHypothesis` records the observed behavioral defect, proposed cause, explanation, evidence citations, conflicts, unanswered questions, provider-reported confidence between 0 and 1, and provider metadata. Confidence is a provider self-report, **not a calibrated probability** and not derived from any statistic. `undetermined` is valid and requires at least one missing-evidence item or question. The ResultsCX needs-analysis cause domains are `knowledge_gap`, `skill_gap`, and `process_gap`; `undetermined` is the explicit fourth value so the schema never forces certainty. A separate performance dimension records the ISD skill-versus-will consideration as `capability` (the evidence suggests the agent could not perform the behavior), `execution` (the evidence suggests the agent could but did not on the cited calls), or `undetermined` (the evidence does not distinguish, or the question does not apply, for example when the cause is a process gap). These are descriptive review labels; they assert nothing about intent or motivation and are not ResultsCX root-cause categories. Neither axis is inferred from fail rates or comment keywords. Text fields are bounded (IDs 128 characters, free text 20,000, lists 200 entries) purely as storage-safety limits.

Provider citations are typed `{item_id, evaluation_id}` references. `signal` is the only aggregate reference and has no evaluation ID. Row references must match both the bundle item ID and its evaluation ID. Duplicate citations, unknown rows, rows from another bundle, incorrect evaluation IDs, and citations on both sides are rejected. Provider output is untrusted: whatever object a reasoner returns (a mapping, or any model instance including subclasses or `model_construct` results) is first reduced to plain data and then re-validated into a fresh, frozen `DiagnosticHypothesis`. Strict schemas, enum values, confidence bounds, required text, length limits, signal association, and citations are all checked before storage; the provider never retains a reference to the stored object. Invalid output fails with a structured error and HTTP 502; citations are never repaired silently. The internal evidence item resolves a citation to original lineage for audit. No raw lineage reference is accepted from a provider. The provider currently supplies `hypothesis_id`; an ID that already exists is refused rather than overwritten.

`DiagnosticReasoner.diagnose(provider_bundle)` is the async replacement point for a future Amazon Bedrock adapter. No AWS account, model, credentials, SDK, or infrastructure is configured in M3. `ControlledTestReasoner` is a test double that returns whatever response it was constructed with and ignores the evidence entirely; it performs no inference and is never installed by the application. The default API provider returns `reasoner_unavailable` (503). An application integrator can inject a real reasoner into `app.state.diagnostics` later without changing the evidence, validation, review, or HTTP contracts.

**Decision:** a new hypothesis starts `awaiting_review`. A reviewer may approve it, reject it with a rationale, or revise it with a rationale and typed corrected result. Revision preserves the original provider hypothesis and citation list; the record enters `revised` and requires a separate approval, after which it stays `revised` with `revision_approved: true`. `approved` and `rejected` are terminal; `revised` accepts exactly one further `approve`. Every other transition is refused with `invalid_state_transition` and leaves no trace. Human revisions pass through the same reduce-and-revalidate step as provider output. Audit events record action, reviewer ID, UTC time, rationale, and the full revision; hypotheses, revisions, and events are frozen value objects, and the service returns deep-copied snapshots, so no caller can alter stored state or history through a returned object. Transitions are serialized with a process lock so concurrent requests cannot record two decisions. `get_approved_diagnosis()` returns only an approved provider hypothesis or an approved human revision, attributed to the single recorded approve event. This is the explicit future Design gate; M3 creates no design or training artifacts.

## API and local operation

Routes under `/diagnostics` list signals, inspect the provider-facing evidence view, create/retrieve hypotheses, approve/reject/revise, and retrieve an approved result. See OpenAPI for request schemas. Normal API errors contain a stable code and short message without confidential row values: 404 for unknown signals or hypotheses, 409 for illegal transitions, 403 for the approval gate, 422 for malformed client input, 502 when the reasoner fails or returns invalid output, and 503 when no reasoner is configured. The evidence route returns the same minimized view a provider would receive, which still includes feedback text; treat it as confidential. Reviewer IDs are plain identifiers; there is no authentication. API state is in memory and is lost on restart; multiple workers do not share reviews, and a duplicate `hypothesis_id` from a provider is refused rather than overwritten. Loading records with duplicate internal IDs fails at startup. To load local M2 normalized JSONL at API startup, set `COACHLENS_API_DIAGNOSTIC_EVALUATIONS_PATH` to the ignored `data/processed/evaluations.jsonl` path. The API starts with an empty signal list when no path is set. A provider must be explicitly installed in the process to create hypotheses. Do not expose this unauthenticated API to untrusted clients or send unreviewed feedback to a remote model.

M3 stops at validated diagnosis and human approval. M4 may build a diagnostic review UI. Training design, simulation, voice, and AWS integration belong to later milestones. Current limits include process-local state, no authentication, no calibrated confidence, no automatic causal inference, known-identity-only feedback redaction (see the privacy boundary above), provider-supplied hypothesis IDs, and no production reasoning provider.

M4 adds read-only, signal-scoped hypothesis listing and a local reviewer evidence route with source lineage. The original provider-facing `/evidence` route remains minimized. See [the M4 workspace guide](m4-review-workspace.md) for the new routes and reviewer privacy limits.
