# M3 diagnostic engine

## Three separate layers

**Fact:** M2 canonical `Evaluation` and `CriterionResult` records establish pass/fail, scores, feedback presence, and source lineage. M3 `PerformanceSignal` reuses M2 `analyze()` for deterministic per-criterion aggregates. It includes zero-failure criteria and ranks by descending fail count, then fail rate, then domain and criterion. This order is a transparent sort, not a ResultsCX severity policy. A signal has no causal category.

**Hypothesis:** `EvidenceBundle` links one signal to only its criterion rows. The aggregate signal and row-level `EvidenceItem` objects are distinct. Each item retains original evaluator feedback and source filename, sheet, and row internally. A provider-facing view drops lineage locations and known employee, evaluator, and leader names from feedback. It retains pseudonymous evaluation IDs, item IDs, original criterion wording, pass/fail, scores, and redacted feedback. The provider view does not guarantee removal of names or other personal information mentioned only inside comments; a deployment must review or strengthen redaction before sending it to a remote provider. Internal M2 IDs are pseudonyms, not an anonymization guarantee.

`DiagnosticHypothesis` records the observed behavioral defect, proposed cause, explanation, evidence citations, conflicts, unanswered questions, provider-reported confidence between 0 and 1, and provider metadata. Confidence is a provider self-report, **not a calibrated probability**. `undetermined` is valid and requires at least one missing-evidence item or question. The ResultsCX needs-analysis cause domains are `knowledge_gap`, `skill_gap`, `process_gap`, and `undetermined`. A separate performance dimension records `capability`, `execution`, `process_or_system`, or `undetermined`. It supports skill-versus-will consideration without asserting that execution difficulty is a ResultsCX root-cause category or equating it with intent. Neither axis is inferred from fail rates or comment keywords.

Provider citations are typed `{item_id, evaluation_id}` references. `signal` is the only aggregate reference and has no evaluation ID. Row references must match both the bundle item ID and its evaluation ID. Duplicate citations, unknown rows, incorrect evaluation IDs, and citations on both sides are rejected. Provider output is untrusted: strict schemas, enum values, confidence bounds, required text, association, and citations are validated before storage. Invalid output fails with a structured error; citations are never repaired silently. The internal evidence item resolves a citation to original lineage for audit. No raw lineage reference is accepted from a provider.

`DiagnosticReasoner.diagnose(provider_bundle)` is the async replacement point for a future Amazon Bedrock adapter. No AWS account, model, credentials, SDK, or infrastructure is configured in M3. `ControlledTestReasoner` returns a supplied typed candidate verbatim for tests and integration development; it does no reasoning. The default API provider returns `reasoner_unavailable` (503). An application integrator can inject a real reasoner into `app.state.diagnostics` later without changing the evidence, validation, review, or HTTP contracts.

**Decision:** a new hypothesis starts `awaiting_review`. A reviewer may approve it, reject it with a rationale, or revise it with a rationale and typed corrected result. Revision preserves the original provider hypothesis and citation list; it enters `revised` and requires a separate approval. Audit events record action, reviewer ID, UTC time, rationale, and the full revision. Rejected and awaiting results cannot cross the Design boundary. `get_approved_diagnosis()` returns only an approved provider hypothesis or an approved human revision. This is the explicit future Design gate; M3 creates no design or training artifacts.

## API and local operation

Routes under `/diagnostics` list signals, inspect provider-safe evidence, create/retrieve hypotheses, approve/reject/revise, and retrieve an approved result. See OpenAPI for request schemas. Normal API errors contain a stable code and short message without confidential row values. Reviewer IDs are plain identifiers; there is no authentication. API state is in memory and is lost on restart; multiple workers do not share reviews. To load local M2 normalized JSONL at API startup, set `COACHLENS_API_DIAGNOSTIC_EVALUATIONS_PATH` to the ignored `data/processed/evaluations.jsonl` path. The API starts with an empty signal list when no path is set. A provider must be explicitly installed in the process to create hypotheses. Do not expose this unauthenticated API to untrusted clients or send unreviewed feedback to a remote model.

M3 stops at validated diagnosis and human approval. M4 may build a diagnostic review UI. Training design, simulation, voice, and AWS integration belong to later milestones. Current limits include process-local state, no authentication, no calibrated confidence, no automatic causal inference, partial feedback redaction, and no production reasoning provider.
