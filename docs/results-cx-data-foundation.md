# ResultsCX data foundation (Milestone 2)

This layer parses the local healthcare QA exports deterministically. It performs no diagnosis, comment summarization, or AI reasoning. Source workbooks and normalized records are confidential local data; Git ignores `data/raw` and `data/processed`.

The only new runtime dependency is `openpyxl>=3.1,<4` for `.xlsx` reading and synthetic workbook fixtures. Existing Pydantic supplies typed records. Python's standard library handles joins, counts, decimal scoring, hashing, and JSONL, so pandas is intentionally omitted.

## Supported source schema

Discovery scans `.xlsx` files beneath `data/raw` and identifies exactly one QA sheet per workbook from its header, independent of filename. The selected sheet may have any name; the current exports use `Export`. All three domains require `QA Name`, `Team Leader`, `AgentNames`, `Date of Call`, `Questions`, `Answers`, `Feedback answers`, `MaxScore`, and `Score`. The domain marker is respectively `Business Pass Count`, `Compliance Pass Count`, or `QA Pass Count`. `Date of Evaluation` is optional and currently occurs only in Compliance. Other columns, duplicate headers, multiple matching sheets, ambiguous markers, missing or duplicate domains, malformed criterion rows, and unreadable workbooks fail with validation errors.

The three inspected workbooks each have an `Export` sheet. Business Process and Member Experience have the nine common fields plus their marker. Compliance has those fields, `Date of Evaluation`, and its marker. Each workbook also has three non-criterion footer or blank rows: a `Total` row (values only in `QA Name`, `Score`, and the pass-count marker), an empty row, and an applied-filters note in `QA Name`. The parser excludes a row only when every column other than `QA Name`, `MaxScore`, `Score`, and the pass-count marker is empty. A row with any identity, question, answer, feedback, or date value must validate as a complete criterion row, so stray evidence is never dropped silently. Values in cells beyond the header columns also fail validation. The observed criterion sets contain 4 Business Process, 10 Compliance, and 9 Member Experience questions per call. These cardinalities are observations, not constants in the parser.

Dates must be Excel dates or ISO dates without a time component. Answers normalize case-insensitive `Yes` to pass and `No` to fail. Any other answer fails. Max and attained scores are nonnegative finite decimals; attained score cannot exceed maximum. The domain pass-count field classifies the source and is cross-checked against the answer: it must be blank, `0`, or `1`, and `1` must coincide with `Yes`. Disagreement fails validation (`answer_marker_conflict`) instead of silently trusting one column. The answer alone defines `passed`; the score is preserved as data and summed in analytics without binary-score assumptions, so a `Yes` with a partial or zero score is accepted and visible in score totals.

## Canonical records and lineage

`Evaluation` groups all criterion rows for one validated cross-domain identity. It contains an internal ID, source agent name, call date, QA evaluator name, team leader, optional evaluation date, and criterion results. `CriterionResult` holds domain, original question, original Yes/No answer, normalized Boolean pass, decimal maximum and attained scores, optional evaluator feedback, and `SourceLineage`. Each lineage points to the source filename, selected sheet, and original 1-based Excel row number (the header is row 1; blank rows keep their numbers). Evaluations are ordered by call date, agent, evaluator, and leader; within an evaluation, criteria follow domain order and then source row order, so reordering source rows changes lineage and criterion order but not identities, values, or statistics. A statistic's `lineages` property gives programmatic access to every supporting criterion row; aggregate serialization excludes that property by default.

The exports contain no reliable evaluation ID. The strict candidate key is the exact, trimmed tuple `(AgentNames, Date of Call as date, QA Name, Team Leader)`. Local inspection found 17 complete identities in each domain; all 17 four-field keys matched across all three domains. Agent and call date alone also happened to be unique in these files, but the implementation uses the additional verified metadata and detects divergent metadata. It requires exactly one occurrence of a given criterion within each domain/key group, rejects missing domain counterparts, and rejects conflicting evaluation dates. A collision check verifies generated IDs are unique in a run.

The internal ID is `rcx1_` plus full SHA-256 of UTF-8 JSON with ordered fields `["resultscx-v1", agent, ISO call date, QA evaluator, team leader]`, no JSON spaces, and unescaped Unicode. It is reproducible across source filenames and row order. This is a pseudonymous technical ID, **not** a source ID or anonymization guarantee: dictionary guesses can reveal names, whitespace trimming can collapse distinct source spellings, metadata changes change the ID, and truly separate calls with identical four fields and the same criterion set cannot be distinguished. If future exports supply a stable call/evaluation ID, the join strategy should be reviewed before use.

## Normalization and analytics

`scripts/profile_results_cx_data.py` prints aggregate-only JSON with filename, sheet names and selection, row counts, column names, non-null and unique counts over criterion rows (footer rows are excluded so evaluator and score cardinalities are not inflated by totals), date ranges, agent/call counts, criterion names, rows per criterion, the distribution of criteria per call, Yes/No frequencies, and feedback coverage. It does not print names, comment text, or criterion-row values. `scripts/normalize_results_cx_data.py` validates discovery and identity, writes one `Evaluation` JSON object per line to `data/processed/evaluations.jsonl`, and prints only domain totals plus the distribution of criterion rows per evaluation (more than one bucket signals uneven criterion coverage). The writer rejects output paths outside a `data/processed` directory, writes to a temporary file that is removed on failure, and replaces the target atomically only after every record is serialized. If validation fails, no output is written and any `evaluations.jsonl` from an earlier successful run is left untouched; check the exit status before consuming the file.

`analyze(evaluations)` calculates a domain total and each domain/criterion statistic from canonical records. Per-criterion buckets use the trimmed question text, matching the duplicate-criterion check, while `CriterionResult.question` keeps the original cell text. `evaluations` is the number of distinct internal IDs represented in that bucket. Pass and fail counts are the number of Yes and No criterion rows. Rates are their counts divided by criterion-row count; a zero denominator yields zero. Feedback coverage is nonempty feedback rows divided by criterion-row count. Score totals are sums of maximum and attained scores, and score rate is attained divided by maximum (zero when maximum is zero). Per-criterion lineage is available only through explicit programmatic access. The current exports have one row per criterion/evaluation, so per-criterion row count equals evaluation count; this should not be assumed for other schemas.

## Privacy and limitations

The JSONL contains employee names and evaluator comments because canonical local evidence must preserve them. Treat it as confidential and do not publish or commit it. Normal profiling and CLI errors expose only aggregates, filenames, schema details, and row numbers. The profile names original QA criteria because criterion-level analysis needs them; review criteria before sharing a profile externally. Tests synthesize placeholder names and comments; CI has no access to real data.

The four-field key is empirically valid for the inspected exports, not universally reliable. Same-key duplicate calls without a source call ID may be impossible to separate. Distinct QA or leader values across domains fail rather than fuzzy-join. A missing criterion that has no duplicate can remain an incomplete evaluation; the parser does not hard-code a required per-call criterion set. Source footer summaries are excluded from calculations. There is no database, API endpoint, UI, LLM, or causal interpretation in this milestone.
